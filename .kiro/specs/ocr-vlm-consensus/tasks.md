# ocr-vlm-consensus - 實施任務清單

## 概述

### 實施範圍

建立可驗證的準確率基準,並以既有雙 OCR 引擎的欄位層共識取代對模型自評信心度的依賴;同時解除雙模態校正的封鎖。第二階段的視覺語言引擎與分層成本控制,依第一階段實測數據決定是否執行。

### 總體工期

**Phase 1**: 約 66 工程小時,另需人工標註約 1.5-2.5 人天(外部人力,不計入工程工時)
**Phase 2**: 約 30 工程小時(條件執行)

### 任務統計

- **主要任務**: 14 個(Phase 1 共 10 個,Phase 2 共 4 個)
- **子任務**: 42 個(另有 1 個無子任務的主要任務,合計 43 個可執行單元)
- **總預估時間**: 約 96 工程小時
- **覆蓋需求**: 需求 1, 2, 3, 4, 5, 6 及非功能性需求(共 6 大項、47 條驗收標準)

---

# Phase 1: 基準與共識

**階段目標**: 建立可驗證的準確率基準,並讓共識機制實際運作。全程不需 GPU,新增基礎設施支出為零。

**工期**: 約 15 個工作天

**交付物**:
- ✅ 可重複執行的準確率基準(取代現行 placeholder)
- ✅ 運作中的欄位層共識機制與欄位級信心度
- ✅ 雙模態 LLM 校正
- ✅ 使用者當場確認流程

## Major Task 2: 基準測試能力

**目標**: 建立可重複執行、會主動拒絕產出無效結果的基準測試能力,取代現行從未實際執行的預置檔案。

### Sub-task 2.1: 實作執行環境檢查與架構守衛

**描述**:
主力 OCR 引擎在特定處理器架構上有上游缺陷會導致程序中止,這極可能是現行基準長期未能產出的原因。基準測試須在執行前檢查環境,不支援時明確拒絕並提示所需環境,而非產出無效數據。

**驗收標準**:
- [x] 執行前檢查處理器架構與主力引擎可用性
- [x] 不支援時拒絕執行並提示所需執行環境
- [x] 拒絕行為不得表現為異常數值或空結果

**對應需求**: 1.10

**依賴**: 無

**預估時間**: 2 小時

**技術要點**:
- 缺陷來源為上游框架對 ARM64 的支援問題,容器繼承主機架構故開發機必然觸發
- 生產與基準測試皆須於 x86_64 執行

**驗收標準**:
- [x] 產出字元錯誤率與欄位準確率
- [x] 產出低信心攔截觸發率
- [x] 結果可持久化為基準線,含引擎組態與執行時間標記
- [x] 可依文件類型分別執行

**對應需求**: 1.3, 1.4, 1.5

**依賴**: 任務 1.2

**預估時間**: 3 小時

**技術要點**:
- 既有評估服務已具備字元錯誤率與欄位準確率計算,可直接複用

- [x] 樣本不足與架構不支援兩種拒絕路徑皆有測試

## Major Task 5: 欄位值正規化

**目標**: 建立「一致」的判準。若無正規化,格式差異會被誤判為引擎不一致,使複核佇列因誤報而塞爆。

**優先級**: P0

---

### Sub-task 5.1: 實作欄位值正規化能力 (P)

**描述**:
依欄位型別提供正規化:識別碼去空白與常見字元誤判、數值去單位與千分位後比數值、日期統一紀年後比對、字串去頭尾空白。須為獨立純函式以利測試。既有格式校正邏輯為**巢狀函式且語意為整段文字替換**,僅可參考其規則,不可直接呼叫。

**驗收標準**:
- [x] 支援識別碼、數值、日期、列舉字串、人名五類正規化
- [x] 未列型別採預設字串正規化
- [x] 實作為獨立純函式,不依賴既有後處理器的內部狀態

**對應需求**: 4.1, 4.2

**依賴**: 無

**預估時間**: 3 小時

**技術要點**:
- 既有後處理器的空白清理為公開方法,可直接使用
- 地號與民國日期的既有轉換規則可作為 regex 樣式參考,但需重寫為接收欄位值的純函式

---

### Sub-task 5.2: 正規化規則的單元測試 (P)

**描述**:
除驗證格式差異不被誤判為不一致外,**必須同時驗證真實差異不會因過度正規化而被誤判為一致**——後者是更危險的失效方向。

**驗收標準**:
- [x] 識別碼、數值、日期各型別的格式變體被判定為一致
- [x] 真實不同的值被正確判定為不一致
- [x] 邊界情況(空值、單邊缺值)有明確行為
- [x] 所有測試通過

**對應需求**: 4.1, 4.2

**依賴**: 任務 5.1

**預估時間**: 2 小時

---

## Major Task 6: 欄位層共識機制

**目標**: 以多引擎一致性作為信心度來源,取代對單一模型自評的依賴,並將訊號送入既有品質判定機制。

**優先級**: P0

---

### Sub-task 6.1: 實作共識解析能力

**描述**:
逐欄位比對多個候選的抽取結果:全部一致時採保守信心度,不一致時壓低信心度,僅單一候選時標記共識不可用而**不得回報高信心度**。須保留各引擎原始值供人工複核對照。

**驗收標準**:
- [x] 全一致、部分不一致、全不一致、單候選四種情境行為正確
- [x] 不一致欄位的信心度被壓低
- [x] 單一候選時標記共識不可用,不回報高信心度
- [x] 保留各引擎原始值於結果中

**對應需求**: 4.1, 4.2, 4.4, 4.5

**依賴**: 任務 5.1

**預估時間**: 3 小時

---

### Sub-task 6.2: 接線各候選的欄位抽取路徑

**描述**:
共識需要各候選分別抽取欄位,但既有抽取能力在條件成立時會觸發 LLM。若對每個候選直接呼叫,LLM 成本將隨候選數倍增。須讓各候選走純規則路徑,LLM 補全僅對共識結果執行一次。

**驗收標準**:
- [x] 各候選抽取階段的 LLM 呼叫次數為 0
- [x] LLM 補全僅對共識後結果執行一次
- [x] 共識模式的 LLM 成本與單引擎模式相同
- [x] 不需變更既有方法的可見性

**對應需求**: 4.1

**依賴**: 任務 4.3, 6.1

**預估時間**: 2 小時

**技術要點**:
- 既有抽取的 LLM 觸發條件為三項同時成立,不傳其中一項即為純規則路徑

---

### Sub-task 6.3: 將共識訊號接入既有品質判定與回應

**描述**:
共識產出的欄位信心度寫入既有頁面結果結構,由既有品質判定機制照常判定是否需複核。判定機制的呼叫方式不得變更。共識明細以選填欄位加入 API 回應。

**驗收標準**:
- [x] 欄位信心度寫入既有結果結構,品質判定介面零變更
- [x] 不一致欄位可觸發既有複核導入流程
- [x] API 回應新增共識明細為選填欄位,既有欄位語意不變
- [x] 共識模式關閉時回應與現行版本一致

**對應需求**: 4.3, 4.7, 6.2, 6.5

**依賴**: 任務 6.2

**預估時間**: 3 小時

---

### Sub-task 6.4: 共識機制的單元測試 (P)

**描述**:
涵蓋共識解析的四種情境、信心度壓低行為、共識不可用標記,以及融合模式切換後既有行為不變。

**驗收標準**:
- [x] 四種共識情境皆有測試
- [x] 驗證共識模式關閉時既有融合行為不變
- [x] 所有測試通過

**對應需求**: 4.1, 4.2, 4.5, 4.7

**依賴**: 任務 6.3

**預估時間**: 3 小時

---

### Sub-task 6.5: 共識啟動與成本的端到端驗證

**描述**:
單元測試無法偵測「共識靜默失效」——因為解析邏輯本身正確,失效點在候選來源。需以端到端流程驗證共識確實啟動,並確認 LLM 成本未增加。

**驗收標準**:
- [x] 端到端流程中共識可用標記為真

      `tests/unit/test_local_only_privacy.py`,環境修復後再遷入整合測試)

**缺口 C1(P1)已修補(2026-08-21,業主裁決後執行)**

原缺陷:`contract_field_extractor.py` 直接建構
`LLMService(provider="openai", model="gpt-4o")`,而 `LLMService.__init__`
從不查閱 `LLM_CLOUD_ENABLED`——那是與 `create_provider` 並存的舊路徑。
獨立 verifier 代理以封死 socket 實測,於全地端組態下仍測得三次對
`api.openai.com:443` 的連線,承載合約 OCR 文字與頁面影像。
且觸發條件是預設組態(`enable_llm` 預設 True,信心度低就觸發)。

修法:守衛下放至 `LLMService.__init__`。放在匯流點而非個別呼叫端,
是因為只要有任何一處直接 new 它,地端承諾就會再破一次。
另於抽取器加前置檢查,讓紀錄講清楚「這是政策決定」而非「LLM 提取失敗」
——只靠守衛兜底的話,值班的人會去查一個不存在的故障。

行為變更:地端組態下合約抽取失去 LLM 輔助,維持正則結果並交由既有低信心
流程處理。流程不中斷。雲端組態(預設)行為完全不變。

## 風險與注意事項

### 高風險任務

- **任務 4.3**(處理器回傳真實候選):**未完成則共識靜默失效,且所有單元測試仍會通過**。任務 4.4 與 6.5 的驗證專為攔截此風險而設,不可略過
- **任務 5.1**(欄位正規化):正規化不足會使不一致率虛高、複核佇列塞爆;過度正規化則會掩蓋真實差異。任務 5.2 須同時驗證兩個方向
- **任務 7**(共識效度實證):若假設不成立,需求 4 的整套機制須重新設計。應在投入任務 8、9 前先取得結果
- **任務 3.1 / 3.2**(標註補齊):依賴外部人力,為關鍵路徑上唯一不可由工程端控制的環節
- **任務 2.1**(架構守衛):現行基準長期無法產出極可能源於此;若守衛未先完成,任務 3.3 會再次失敗
