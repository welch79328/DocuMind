## 現在卡在哪裡

**三件事沒拍板就不能開工**（詳見 [02 §7](./02-V1-SCOPE.md#7-需業主拍板的三件事)）：

| # | 決策 | 不決定的後果 |
|---|------|-------------|
| 1 | 租戶**內**的角色範圍 | 一位基層承辦問「所有準時率低於七成的租客」就會拿到全租戶名單，而 CI 的跨租戶測試不會亮紅燈 |
| 2 | 敏感欄位輸出白名單 | 答案會攜帶欄位原值與可複製的 SQL；與決策 1 疊加後外洩面是整個租戶的個資 |
| 3 | F6 金流對帳怎麼處置 | `payment_collections` 0 列且三個 checkout 零引用，做了就是一個永遠回空清單的功能 |

加上兩件同時要拍板的：**「答錯」回報路徑**（[05 §3.5](./05-PREREQUISITES-AND-ACCEPTANCE.md)）——
沒有它，信任層的驗收永遠量不到。

## 三條貫穿全部文件的原則

### 1. 禁止推測

每一句關於 JGB 現況的敘述，都要能指回**檔案路徑、可 grep 的符號、或一句 SQL**。
查不到就寫「查不到」，不寫「應該有」。

**查詢必須指定 `--default-character-set=utf8mb4`**——
不指定時中文註解會回成 `??????`，所有「註解含某中文詞」的否定結論會自動變成「不存在」。
查法有效性的正對照：`column_comment LIKE '%合約%'` 應回 327 筆。

### 2. 否定結論要附正對照組，而且正對照組本身要是真的

回報「沒有／不存在」之前，同一次查詢裡必須包含一個**已知必然存在**的項目。

**第二輪查證發現初版有兩個壞掉的正對照**：
一個用了 dev schema 裡根本不存在的表（`iot_manufacturers`），
一個用了已經改名的類別名（`BuildingTranscriptParser`）——
**拿一個不存在的名字去 grep，零命中證明不了任何事。**

正對照組一律寫出**被命中的具體欄位或檔案**，不寫筆數
（初版六組筆數第二輪沒有一組重跑得出來）。

### 3. 拒答的品質決定信任

答不出來時老實說，比答得出來的部分更能決定承辦信不信這個系統。
硬答一題沒有資料的問題是 **P0 bug**，不是體驗問題。
**把系統故障渲染成「系統沒有這個資料」，同樣是 P0。**

## 這份規格的前提與作廢條件

**前提**：三週商業查證通過——量體夠、有人願意付、競品沒有。

需要的三個數字（尚未取得，由業主提供）：

1. 目前客戶數與平均月費
2. 年流失率與流失原因
3. 近 12 個月因為「缺某個功能」而輸掉的案子數

**作廢條件**：若查證結果是量體不足，這份規格的正確處置是**整份作廢**，
不是縮小範圍再做一次。範圍已經是從資料反推的最小值了，再縮就只剩一個查詢介面。
