# 第一部分：三項 P0 前置工作

這三件事必須在**第一支查詢寫出來之前**完成，否則會做出一個會洩漏資料的東西。

---

## 1. P0 — 租戶邊界規約

### 問題

`bills` 有**六個當事方角色欄位**：

```
role_id
owner_role_id
lessor_role_id
lessee_role_id
creditor_role_id
issue_target_role_id
```

再加四個操作者角色欄位（`pay_user_id` / `pay_user_name` / `pay_role_id` / `pay_role_menu_name`）。

而 `details`、`invoices`、七張合約衛星表**完全沒有租戶欄位**——
它們靠 `bill_id` / `contract_id` 繼承。這在 schema 設計上正常，
**但沒有任何規約強制查詢必須走那條繼承路徑。**

### 要求

先訂一份文件：**每一種查詢用哪一個欄位隔離、為什麼。**

讓每個功能各自決定，遲早會有一個把別家業者的資料算進去。

### 驗收

建**兩個測試租戶**，交叉問每一個功能（F1–F10），**零筆越界**。
**這條測試進 CI**，每次 commit 都跑。

## 2. P0 — 推導定義的單一來源

### 問題

第一版有三個**沒有現成欄位、必須推導**的指標：

| 指標 | 用在 | 推導自 |
|------|------|--------|
| 逾期未簽 | F2 | `contract_expire_at` + `bit_status` |
| **逾期天數** | F3、F4 | `date_expire` + 實繳日 |
| 帳齡分組 | F3 | 逾期天數 |

**全文統一用「逾期天數」一詞**——初版 F4 另稱「遲繳天數」，
名稱一分岔，F4 就會寫成不帶特例的第二套算法，於是 F3 與 F4 對同一張帳單給出不同天數。

### 這份定義必須寫死的五件事

1. **沿用 `app/Bill.php` 既有的逾期判定，不自己重寫。** 它有兩個非直覺的既有行為：
   補開帳單（`date_expire` 早於 `created_at`）不算逾期；設定檔名單內的特定租戶滯納金不算逾期。
   重寫會造成「**AI 說 8 件、後台顯示 6 件**」——最傷信任的一種錯，
   因為承辦無法判斷是哪一邊錯了，最後兩邊都不信。
2. **`bills.date_expire` 是 `int` 不是日期型別**，不能直接套日期函式，轉換方式要寫死。
3. **實繳日用 `pay_at`（timestamp，30/525）還是 `pay_ymd`（int，22/525）**——
   兩者填寫率不同且都偏低，**開工前必須先確認哪一個是權威**，結論寫進這份定義。
4. **日界處理**：以日期截斷相減或時間戳相減、時區為何。
5. **準時率的分母**：`status = 16 (BILL_COMPLETE)` 且 `active = 1`。

### 驗收

三個推導指標各寫成一份可複驗的 SQL，放進 repo，
並在答案的「這是怎麼算的」展開區**直接引用同一份定義**。

## 3. P0 — 租戶內的角色範圍（待拍板）

### 問題

§1 只擋跨租戶。**同一租戶內沒有任何範圍規約。**

F4 的輸出是逐租客準時率、F7 是逐件揭露紅旗、F1 的稽核軌跡含承辦姓名快照；
家庭成員、所得、緊急聯絡人就在 `contracts` 與 `lessee_datas` 裡。

照現規格實作，**一位基層承辦問「所有準時率低於七成的租客」就會拿到全租戶名單**，
而 §1 的 CI 跨租戶測試**不會亮紅燈**。

### 要求

列出第一版允許的角色，逐 F1–F10 標明每個角色可查詢的列範圍
（自己經手的合約／所屬團隊／全租戶），以及該範圍靠**哪個欄位**過濾。

**預設建議**：只開「所屬團隊」一種範圍。

→ 決策見 [02 §7](./02-V1-SCOPE.md#7-需業主拍板的三件事)。

### 驗收

以**同租戶但不同角色**的兩個帳號交叉問 F1–F10，**零筆超出該角色被授權範圍**。

## 4.5 安全層

- [ ] 跨租戶測試**零筆越界**，且此測試**進 CI**
- [ ] **同租戶跨角色**測試零筆超出授權範圍（§3）
- [ ] 輸出白名單測試：對含敏感欄位的合約各問一次 F1–F10，
      **答案與展開 SQL 中零次出現未遮罩原值**
- [ ] 第一版**唯讀**：無任何寫入 JGB 庫、無任何對外送出
- [ ] 以**只有 SELECT 權限的資料庫帳號**執行，且**以實際連線驗證**（嘗試 INSERT 應被拒）

> 註：JGB 目前的應用帳號持有 `GRANT ALL PRIVILEGES`。第一版**不得**沿用該帳號。

## 5. 非功能需求

初版完全沒有這一節，於是實作者最省事的做法就是沿用應用層既有連線＝**主庫**。
第一版讓承辦用自然語言觸發臨時聚合 SQL，打在 78,465 列、344/633 欄位低填充、
部分無索引的正式庫上——**一個帳齡分組全表掃描就可能拖垮租管後台**。

| 項目 | 要求 |
|------|------|
| 連線 | **一律唯讀複本**，不得使用應用層既有連線 |
| 單次查詢逾時 | 上限 **10 秒**。逾時即中止並回**狀態④（系統故障）**，不得渲染成拒答 |
| 併發 | 同時查詢數上限需設定（建議先設 3，依複本負載調整） |
| 資料新鮮度 | 複本延遲的可接受上限需設定，並**在答案上揭露資料時點**（例如「資料截至 14:30」） |
| F3 驗收時點 | 逐筆比對須在**複本延遲已追平**時執行，否則會偽陽性失敗 |

## 7. 下線程序

「可隨時下線」只證明了「沒有殘留資料結構」，**沒有證明有人知道怎麼關、什麼情況要關**。

| 項目 | 內容 |
|------|------|
| 關閉方式 | **撤銷該 SELECT 帳號權限**（一個動作，不依賴程式部署） |
| 觸發條件 | 出現任一硬答 P0／跨租戶或跨角色越界一筆／複本延遲超過上限／正式庫負載告警 |
| 決策人 | 待指定 |
| 通知對象 | 首批使用的承辦 |
| 下線訊息 | 須符合 [04 §2](./04-REFUSAL-SPEC.md#2-拒答不是錯誤訊息是一句可行動的說明) 的規則——**不得把事故說成產品排程** |

## 8. 信任層（決定第二版做不做）

| 指標 | 可量測的定義 | 門檻 |
|------|-------------|------|
| 持續使用 | 一位承辦在一週內問出**至少 3 個非重複問題**，且非由專案成員代打，計為該週「主動使用」 | 連續 4 週，**至少 2 位承辦**達標 |
| 錯誤可歸類 | 每一筆「答錯」回報都要能歸類成「資料問題」或「查詢問題」 | **全數可歸類** |
| 與後台一致 | 統計期間內 F3 與後台帳單列表頁的件數比對 | **差異次數為零** |

**三項都達標才討論第二版。** 任一項未達標，先修這一項，不加功能。
