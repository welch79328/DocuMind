# 02 — 第一版範圍

> v2.0：第二輪查證後修訂。範圍縮小一項（F6 暫停）、硬約束從三條增為五條。

---

## 1. 一句話

**讓承辦用問的，取代開三個頁籤篩選。**

問題限定在「合約與帳務的狀態、時間、件數」，加上物件現況揭露的紅旗。

**不碰文件內容、不碰無法用單一權威定義寫死的推導指標。**
第一版只允許三個推導指標——**逾期未簽、逾期天數、帳齡分組**——
其定義單一來源見 [05 §2](./05-PREREQUISITES-AND-ACCEPTANCE.md#2-p0--推導定義的單一來源)。

> 用語約定：本組文件的「承辦」＝第一版使用者，指單一團隊的 2–3 位案件承辦人員。
> 全文不再混用「使用者」指稱這群人。

## 2. 做什麼

- **九個唯讀查詢功能**，全部建立在[實查確認可用的 12 個資料源](./01-DATA-INVENTORY.md#1-十二項現在就能用)上
- **每個答案附出處**：這個數字從哪張表、哪個欄位、用什麼條件算出來的
- **問到系統沒有的資料時明確拒答**，並說明缺什麼、可以改看什麼

功能清單見 [03-FUNCTIONAL-SPEC](./03-FUNCTIONAL-SPEC.md)：

| ID | 功能 | 優先級 |
|----|------|--------|
| F1 | 案件走到哪一段 | P1 |
| F2 | 簽署進度與逾期未簽 | P1 |
| F3 | 應收與逾期清單 | P1 |
| F4 | 繳款準時性 | P1 |
| F5 | 發票狀態盤點 | P1 |
| ~~F6~~ | ~~金流對帳缺口~~ | **暫停，待拍板** |
| F7 | 物件現況揭露紅旗 | P1（投報率最高） |
| F8 | 通知成本與失敗盤點 | P2 |
| F9 | 社宅補助申請盤點 | P2 |
| F10 | 附件有無清單 | P2（新增，見 §2.1） |

### 2.1 為什麼 F6 暫停、F10 新增

**F6 暫停**：初版把 `payment_collections` / `collection_settlements` 評為「全庫品質最好的一組」，
第二輪查證發現**兩張表各 0 列，且 dev1/dev2/dev3 三個 checkout 的 PHP 全部零引用**。
那組受控狀態字串只存在於 `column_comment`，沒有任何程式碼常數背書。
判定與第 2 節對 `contract_documents`（0 列）的標準一致：**建了表不等於能用**。
→ 這一項是[待拍板決策之一](#7-需業主拍板的三件事)。

**F10 新增**：[04 拒答規格](./04-REFUSAL-SPEC.md)的第 1、3、4 題把替代指向「附件有無清單」，
但原本沒有任何功能提供它——**拒答不能承諾系統給不出的東西**。

## 3. 不做什麼，以及為什麼

| 不做 | 理由 |
|------|------|
| 文件抽取結果的內容問答 | 抽取管線**是存在的**（`TranscriptParserService` + DocuMind `multi_type_ocr`），但結果只落在 `transcript_parse_jobs.result` 的 JSON blob，要人工確認才寫回 `estates`，且 dev 庫 0 筆。**這是成熟度問題不是存在性問題**，見 [01 §3.5](./01-DATA-INVENTORY.md#35-文件欄位抽取初版判定錯誤管線是存在的) |
| 任何跨帳單金額加總 | `bills.total` / `payments.price` / `repairs.total` 全是浮點，會有尾差。例外見 §4.1 |
| 依屋齡分組 | `estates.age` 是匯入當下的死值，不隨時間更新，61 筆中僅 1 筆非 NULL 且 `> 0` 為 0 筆 |
| 空置天數、空置率 | **不是沒有基礎資料，是三套口徑互相矛盾**（`UserController::overview`、`Community::getQuantitiesOfIdle`、`EstateController` 空置率區塊）。要先統一口徑，第一版不做 |
| 招租曝光 | 站內 `estate_view_counts` 是瀏覽數，不等於外部平台曝光 |
| 費用分類統計 | 分組主檔活在 `app/ItemGroup.php::DEFAULT`（13 個受控分組），但 **62 個品項中 37 個未分組**，`nature` / `accounting_code` 62 筆全 NULL |
| 申報狀態、社宅退件與核定 | 純匯出無回寫，系統不知道申報過沒有 |
| 廠商比價 | 廠商主檔不存在，`manufacturer_id` 在 `RepairController` 裡兩處是被註解掉的 |
| 客訴與爭議統計 | 無工單表，且**連推導路徑都沒有** |
| 報修相關的一切 | 第一版不碰 `repairs`（dev 僅 3 筆，且 `PROCESS` 段無時間戳） |
| 任何對外送出 | 第一版**唯讀**。系統已有數十條自動對外路徑，不再增加（**「30 條」是初版未附證據的斷言，已撤下**——要用精確數字須先訂出可重跑的口徑） |
| 寫回任何欄位 | 同上。寫回需要「前值→還原」機制，而還原目前不存在 |

## 4. 五條硬約束

### 4.1 金額只給件數，三個例外

不能加總的：`bills.total`（float(20,5)）、`payments.price`（float）、`repairs.total`（float(10,2)）。

**判準：欄位型別為 `int` 或 `decimal` 才可加總金額。** 目前符合的三處：

| 例外 | 型別 | 用在 |
|------|------|------|
| 發票金額 | `int` | F5 |
| 社宅補助**申請**金額 | `int` | F9（不含核定與撥款） |
| 代收對帳金額 | `decimal(12,2)` | ~~F6~~（表為空，隨 F6 一併暫停） |

其他一律回件數。承辦問「總共收了多少」時，改答件數並說明原因。

### 4.2 逾期判定沿用既有實作，不自己重寫

用 `app/Bill.php` 既有的逾期判定邏輯。它有兩個**非直覺但刻意**的既有行為：

1. 補開帳單（`date_expire` 早於 `created_at`）**不算逾期**
2. 設定檔名單內的特定租戶滯納金**一律不算逾期**

重寫會造成「AI 說 8 件、後台顯示 6 件」——這是最傷信任的一種錯。

### 4.3 一律 `active = 1`，一律連唯讀複本

**`active = 1`**：所有主表都有軟刪欄位（`ACTIVE_NORMAL=1` / `ACTIVE_ARCHIVED=0` / `ACTIVE_SOFT_DELETED=99`，
`invoices` 走 `deleted_at`）。**`contracts` 282 筆裡 `active=1` 只有 146 筆**——
漏掉這個條件，答案會把封存合約算進去。

**唯讀複本**：查詢**不得使用應用層既有連線**。第一版讓承辦用自然語言觸發臨時聚合 SQL，
打在 78,465 列、344/633 欄位低填充的正式庫上，一個帳齡分組全表掃描就可能拖垮租管後台。
非功能上限見 [05 §5](./05-PREREQUISITES-AND-ACCEPTANCE.md#5-非功能需求)。

### 4.4 輸出欄位白名單（待拍板）

規格要求「答案附出處、可展開這是怎麼算的」，這代表答案會攜帶**欄位原值與可複製的 SQL**。
統編、身分證、生日、電話、門牌、家庭成員、所得、緊急聯絡人全都在 `contracts` 與 `lessee_datas` 裡。

**沒有白名單，實作者預設會全部帶出。**

→ 這是[待拍板決策之二](#7-需業主拍板的三件事)。在拍板之前**不得開工**。

### 4.5 不動 schema、不寫回、不對外送

第一版**不需要新增任何 JGB 資料表或欄位**。這是刻意的：
它讓第一版可以在不動 schema 的前提下上線與下線（下線程序見 [05 §7](./05-PREREQUISITES-AND-ACCEPTANCE.md#7-下線程序)）。

執行帳號**只給 SELECT 權限**——用權限保證，而不是靠程式自律。

> 例外：問答本身的使用紀錄需要落地，但**不得寫回 JGB 庫**，見 [05 §6](./05-PREREQUISITES-AND-ACCEPTANCE.md#6-稽核與使用紀錄)。

| 資料源 | 歸屬 |
|--------|------|

| 2 合約簽署時間軸 | F2 |

| 4 繳款準時性 | F4 |
| 5 發票生命週期 | F5 |
| 6 金流交易（`payments` / `payment_atm_nos`） | **不做**——F6 暫停後，單獨的 `payments` 44 列不足以支撐獨立功能 |
| 7 通知成本與結果 | F8 |
| 8 廣告瀏覽逐日 | **不做趨勢功能**，僅作為 [04 第 14 題](./04-REFUSAL-SPEC.md)的拒答替代，由 F10 一併提供 |
| 9 社宅補助申請 | F9 |
| 10 物件現況揭露 | F7 |

## 7. 需業主拍板的三件事

這三件不是「開放問題」，是**擋住開工的決策**。

| # | 決策 | 預設建議 | 不決定的後果 |
|---|------|---------|-------------|
| 1 | **租戶內的角色範圍**——第一版允許幾種角色，各自看得到自己經手的案子／所屬團隊／全租戶？ | 建議只開「所屬團隊」一種範圍，靠 `contracts` 的團隊欄過濾 | 一位基層承辦問「所有準時率低於七成的租客」就會拿到全租戶名單，而 CI 的跨租戶測試**不會亮紅燈** |
| 2 | **敏感欄位輸出白名單**——身分證、統編、生日、電話、門牌、家庭成員、所得、緊急聯絡人能不能出現在答案與展開區？ | 建議一律禁止輸出，必要識別欄位遮罩（例如身分證僅顯示首尾各一碼） | 答案會攜帶原值與可複製的 SQL，與決策 1 疊加後外洩面是整個租戶的個資 |
| 3 | **F6 怎麼處置**——砍掉，還是降級為「已建表未啟用」等日後啟用？ | 建議砍掉，等 `payment_collections` 有實際寫入再談 | 做出一個永遠回空清單的功能，第一次使用就砸信任 |
