# 謄本解析：現況、決策與待辦

> 最後更新 2026-10-15 ／ 線上版本見 §3（54.248.201.66）
> 驗收範本、跑法與量測結果見 [`docs/testing/transcript-online-acceptance.md`](../testing/transcript-online-acceptance.md)；
> 對接格式見 [`docs/api/INTEGRATION.md`](../api/INTEGRATION.md) §3.1。

## 1. 目標（業主定案）
- **電子謄本上印的每一項都要解析出來、而且讀對**；凡是需人工或未解析的欄位，要說得出原因。
  不限下游 jgb2 用到的欄位（業主：「不用管 jgb 謄本要能都被解析出來」）。
- **實際要處理的謄本是電子檔**。掃描／拍照件（OCR 品質、速度、多頁 OOM、AI 補值）排到**提升機器規格之後**。
- 修法一律通用，不打特規（業主：「禁止特規修改 需通用修改」）——不列碼位、字元清單或特定字串，改用依性質或版面定義的規則。

## 2. 現況：電子謄本
| 項目 | 狀態 |
|---|---|
| 25 個單值欄位＋6 種清單 | 正確；三份真實謄本皆不需人工 |
| 全文 `document_fields.transcripts` | 土地、建物謄本上印的每一項依原文標籤回傳（含住址、權狀字號、他項權利部整段、地目、公告土地現值、謄本檢查號）；5 份電子謄本逐字對帳 0 遺失 |
| 值掛在對的標籤、筆、張 | 2026-10-14 逐項全面核對（不是抽查）：5 份共 11 張、28 個部、396 個頂層項目（另含頁首），每一個「標籤:值」對照原文，**0 錯**。方法：本機用線上同版 PyMuPDF 1.24.13 抽文字層，跑 `parse_transcript_pages`，與原文逐行並排 |
| 值內混有說明句 | `謄本檢查號`／`謄本種類碼` 的值帶著同一行後半句（如 `…8806,可至:http://land.hinet.net 查驗本謄本之正確性`），原文就印在同一個標籤後面，照原文保留；要純代碼需在下游取第一個逗號前 |
| 原文被回傳的比例 | 約 15% → 100% |
| 速度 | 40–72 ms／份（伺服器端） |
| 車位 | **未完成**：公設車位行保留為文字未拆；無電子樣本可驗 |
| 固定輸出格式 `document_fields.transcript_records` | 每張謄本一筆、鍵固定（依官方格式），沒印回 `null`／`[]`，附 JSON Schema（`docs/api/transcript_records.schema.json`）、判定 有／未見／無法判定。5 份電子謄本：11 張全部符合 Schema、640 個原文值每個都有去處、「其他欄位」0 項 |

## 4. 決策紀錄（2026-10-14）
| 決策 | 理由 |
|---|---|
| 全文解析依版面結構讀，不再逐欄加規則 | 逐欄補規則永遠補不完，也是特規；謄本有什麼標籤就讀什麼 |
| 標籤用謄本原文，不翻成英文鍵名 | 對照表就是逐欄清單（特規），且謄本標籤會隨版本增減 |
| 原文空白（`(空白)`、`民國---年--月--日`）在 25 欄回 `null`、信心度 0.9 | 原文印空白是「讀到了空」；若當成讀不到，必填欄位印空白的謄本（長春路、懷寧街的主要用途）會白白進複核 |
| 一頁認不出是哪一部時，照舊要求全部必要欄位 | 放寬會拆掉「土地持分被誤補進建物權利範圍」（0658077 的災情）唯一的攔截——複核 |
| 合約不套用空白標記與「冒號前空白」規則 | 合約信心度以有無值計算；冒號規則實測會把甲方地址、電話填進乙方欄位 |
| 車位先不拆欄位 | 「權利範圍」前是逗號，若改成逗號後也算標籤會切壞謄本檢查號等值；需真實電子樣本再定規則 |
| 掃描件讀取規則（G5）暫停 | 實際資料是電子檔；掃描件問題排到升級機器之後 |
| 謄本改為固定輸出格式（TFS，業主 2026-10-14 選定） | 鍵跟著謄本原文變，下游無法對；jgb2 表單 31 欄固定、10 欄需人工。固定鍵依官方謄本格式，表外項目進「其他欄位」不丟 |
| 判定只輸出 有／未見／無法判定，不輸出「無」 | 「未見」只表示謄本上沒印；說「無」講錯會直接改變判斷（jgb2 `6c4da96339`）。比對詞取自地政司代碼表、整串相等；沒有類別的舊版註記一律無法判定 |
